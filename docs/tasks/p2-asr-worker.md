# Task p2-asr-worker: ASR worker process: sherpa-onnx Parakeet TDT v3 + Silero VAD, word timestamps, JSON-lines server, 1 h bench

## Scope
src/Murmur.Transcription/**, tests/Murmur.Transcription.Tests/**, Directory.Packages.props (sherpa-onnx runtime packages only)

## Spec
Murmur.Transcription is the separate ASR worker process (models never live in the app process). Protocol: src/Murmur.Core/Transcription/Protocol/WorkerProtocol.cs (architect-owned; read it first — command line, request/event kinds, JSON context).
1. Native layer: port the spike's blittable [LibraryImport] layer over the sherpa-onnx C API (v1.13.8) into src/Murmur.Transcription/Native, production quality, with [assembly: DisableRuntimeMarshalling]; strings marshalled as UTF-8 (paths with Cyrillic must work — test one on Linux; Windows behaviour UNVERIFIED). Reference the per-RID native runtime packages (e.g. org.k2fsa.sherpa.onnx.runtime.linux-x64 / .win-x64 — check exact ids and that they contain sherpa-onnx-c-api + onnxruntime) instead of the 9-RID meta-package, selected by RuntimeIdentifier (and for a plain `dotnet build` on Linux/Windows the host RID). Add the Silero VAD C API (SherpaOnnxCreateVoiceActivityDetector etc.). Struct-layout tests against sizes/offsets from c-api.h (the spike measured them with clang; re-measure any new struct the same way).
2. Pipeline: stream the 16 kHz mono WAV (PCM16 or float32; reject anything else with a clear error) in chunks (never load a 1 h file at once) through Silero VAD (threshold ~0.5, min silence ~0.3 s, min speech ~0.25 s, max speech 15 s so segments stay <= 15–20 s; split anything longer) -> decode segments in batches with DecodeMultipleOfflineStreams (batch size tuned, e.g. 8) using NumThreads = --threads (default Environment.ProcessorCount) -> text + token timestamps (+ durations) -> words: a token starting with U+2581 (or a space) begins a new word; word start = its first token time; word end = last token time + duration (or next word start / segment end). Absolute times = segment start + token time. VAD before ASR matters: the spike showed one decode over mixed languages drops the second language.
3. Server mode `--serve --model-dir <dir> --vad <file> [--threads N] [--idle-exit-seconds S (default 120)]`: emit `ready`; read WorkerRequest lines from stdin; transcribe jobs one at a time (queue others); load the model lazily on the first transcribe; stream `progress` (after each batch) and `segment` events in time order, then `done`; `cancel` (same requestId) stops promptly between batches with an `error` event Error="cancelled"; `ping` -> `pong`; `shutdown` or stdin EOF -> exit 0; idle for S seconds -> exit 0 (frees model memory). Malformed line -> `error` event, keep running. Unhandled exception -> `error` event, exit 1. Only protocol JSON on stdout (flush per line); diagnostics to stderr.
4. Bench mode `--bench --model-dir <dir> --vad <file> --wav <file>[,<file>...] [--seconds 3600] [--out <json>]`: build an N-second 16 kHz signal by concatenating the wavs with 0.5–1.5 s silences (deterministic), run the same pipeline, print/write JSON {audioSeconds, loadMs, transcribeMs, rtf, realtimeFactorX, segments, words, threads, batch, machine{os, cpu, cores}}. Also `--transcribe <wav>` prints the text (debug).
5. Tests (tests/Murmur.Transcription.Tests): struct layouts; word building from tokens (pure); WAV reader edge cases; protocol round trip by launching the real worker process (locate the built worker next to the test assembly or via its project output; `dotnet <dll>` is fine): transcribe test_wavs/en.wav when models exist (MURMUR_MODELS_DIR or /root/models; skip with a message otherwise) -> text contains "country", word times monotonic and inside the audio; cancel; idle exit with a short timeout; malformed request; non-16 kHz WAV rejected.
6. Measure and report (machine info!): Linux AOT publish of the worker (0 warnings, size of exe + native libs); the 1-hour bench on this 4-vCPU machine built from the four test wavs (target < 180 s = criterion of phase 2; if slower, tune batch/threads/VAD and report the best configuration); peak RSS of the worker.
